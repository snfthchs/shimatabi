この文書は、実装を始める前の最後の計画である。テストで何を確かめるか、提出までに何を作るか、実装をどのIssueに分けるかを決める。

## 1. 今回決めたこと

| # | 決めたこと | 理由 |
|---|---|---|
| 1 | **テストは、APIテストを中心にし、画面は手動のデモチェックリストで確かめる** | リスクの高い定員・認可・個人情報は、APIを直接呼ぶテストで速く安定して確かめられる。画面の自動テスト（E2E）は、準備と安定化に時間がかかる |
| 2 | **テストの時間は、各区間に含め、実装と同時にAIに書かせる**。総時間は5:00のまま | テスト専用の枠を足すと、予備枠が減る。代わりに、チェックポイントを増やして遅れを早く見つける |
| 3 | **提出は、GitHubのリポジトリを非公開のまま共有（招待）する** | 履歴とPRも見てもらえて、AI活用の説明に役立つ |
| 4 | **提出用の設計資料は、図つきの要約版（2〜3ページ）を1つ作る**。今の `docs/` は詳細として添える | 「簡単な設計資料」という要求に合う |

## 2. テスト計画

### 2.1 方針
- **リスクの高いものから確かめる。** 定員（ダブルブッキング）、認可、個人情報は、壊れたときの影響が大きいので、最優先にする。
- **数を絞る。** 5時間の中なので、網羅ではなく、重要な振る舞いを確実に確かめる。
- **実装と同時に書く。** テストは、AIが実装と同時に書き、人間が内容を確認する。確認で手直しが必要だった点は、`docs/ai-dev-log.md` に記録する。
- 結果は隠さない。失敗したテストや、実行しなかった確認は、そのまま報告する。

### 2.2 テスト対象

| # | 対象 | 確かめること | 優先度 |
|---|---|---|---|
| 1 | 定員 | 満席の便への予約が `SLOT_UNAVAILABLE`（409）で断られる。**複数スレッドから同時に予約しても、定員を超えない**。却下すると定員が解放される。承認しても定員は変わらない。開始後の便には予約できない | P0 |
| 2 | 認可 | 未ログインで事業者向けAPIを呼ぶと401。他の事業者の予約は、一覧に出ず、承認・却下・連絡先の表示が404になる | P0 |
| 3 | 個人情報 | DBに保存された氏名・電話・メールが暗号文で、平文でない。事業者の一覧はマスク済み。「連絡先を表示」は自社の予約だけ。ログに個人情報が出ない | P0 |
| 4 | 予約の流れ | 即時確定の体験は `confirmed`、承認制は `pending` になる。承認・却下ができる。すでに処理した予約を再度処理すると `INVALID_STATE`（409）。予約の確認は、番号と連絡先が一致したときだけ成功し、不一致は同じ404 | P0 |
| 5 | AIモック | 例文から、日付・時間帯・子連れ・雨・那覇からの距離などの条件を取り出せる。条件に合う候補がないときの返答。提案は、DBにある体験だけ | P0 |
| 6 | 認証 | ログインの成功と失敗（失敗のメッセージは同じ）。ログアウトでセッションが無効になる。期限切れのセッションは401 | P0 |
| 7 | 入力検証 | 電話番号・メールの形式、人数が1以上で残席以下であること、必須項目の欠落 | P1 |
| 8 | 依存関係・秘密情報 | 依存パッケージの脆弱性チェックを実行して結果を記録する。`.env` や鍵が、コミットに入っていない（コミット前に確認する） | 秘密情報の確認はP0、脆弱性チェックはP1 |
| 9 | デモの流れ | 2.5節のチェックリストを、手動で通す | P0 |

### 2.3 テストの環境とデータ
- バックエンドのテストは、FastAPIのテスト用クライアントでAPIを呼ぶ形で書く（ツールの選定は、実装の開始時に決める）。
- テスト用のDBは、テストごとに作り直す。**同時実行のテストでは、一時ファイルのSQLiteを使う**（メモリ上のDBは、スレッド間で共有が難しいため）。SQLiteは同時に書き込めないので、待機の設定を入れて、テストが不安定にならないようにする。
- データは、テストごとに作るもの（フィクスチャ）を使い、シードに依存しない。事業者は認可のテスト用に2社、体験は即時確定と承認制の2種類、便は定員が小さいもの（例: 3名）を用意する。氏名・電話・メールは、すべて架空の値にする。
- 暗号化の鍵は、テスト用の架空の鍵を、テストの中で環境変数として設定する。本番の鍵は使わない。
- **同時実行のテストの組み立て**: 定員Nの便に、N人を超える数の予約を複数スレッドで同時に送る。成功した予約の人数の合計が、定員を超えないこと、失敗した予約が409になることを確かめる。

### 2.4 フロントエンド
自動テストは作らず、型チェック、lint、ビルドが通ることを確かめる。画面の動作は、手動のチェックリスト（2.5節）で確かめる。

### 2.5 デモのチェックリスト（手動）
[設計の概要](design-overview.md)の7.1節の流れに、確認を加えたもの。

- [ ] スマホ幅の画面で、AIコンシェルジュに「今日の午後、那覇から行ける子連れOKの体験ある？」と聞くと、提案が出る
- [ ] 提案から、承認制の体験の詳細に進み、予約できる。「承認待ち」と予約番号が出る
- [ ] 事業者の画面に、ログインIDとパスワードでログインできる。承認待ちの予約が見える
- [ ] 氏名・電話・メールが伏せ字で出ている。「連絡先を表示」で、全体が見える
- [ ] 予約を承認できる
- [ ] 旅行者の画面で、予約番号と連絡先を入れると、「確定」と表示される
- [ ] 連絡先を間違えると、予約が見つからない旨の表示になる
- [ ] 満席の便には、予約できず、断られる
- [ ] ログアウトすると、事業者の画面に入れない（予約一覧のURLを直接開いてもログインへ戻る）
- [ ] 他の事業者でログインすると、最初の事業者の予約が見えない
- [ ] （P1）便を中止にすると、参加者への連絡文が出る

### 2.6 品質ゲート
- **各PRの前に**、次を実行し、結果をPR本文に書く（ワークフローのとおり）。
  - バックエンド: テスト、lint、（型チェックを入れる場合は）型チェック
  - フロントエンド: 型チェック、lint、ビルド
- 具体的なツールとコマンドは、実装の開始時に決め、`AGENTS.md` の「コマンド」に書く。
- **CI（GitHub Actionsなど）は、予備枠で時間が余ったときの対応（P2）とする。** CIがない間は、人間とAIがローカルで実行した結果を、PR本文に残す。

### 2.7 時間と、縮小する順番
- 時間の目安（[時間計画](non-functional-and-infra.md)に反映済み）: 区間3に約25分、区間4に約5分（型チェック・lint・ビルド）、区間5に約10分（手動のチェックリスト）。
- 区間3には、セキュリティの実装（約25分）も含まれるので、**AIにテストを実装と並行して書かせる前提**で見積もっている。余裕は少ない。
- 時間が足りないときは、次の順にテストを縮小する。
  1. 入力検証（#7）と、脆弱性チェックをやめる
  2. 認証（#6）の細部をやめる（ログインの成否と、ログアウト後の無効化だけ残す）
  3. AIモック（#5）を、代表的な例文だけにする
- **定員（#1）、認可（#2）、個人情報（#3）は、縮小しない。**

## 3. 成果物の計画

### 3.1 成果物の一覧

| 成果物 | 内容 | 形式 | 作る時期 | 担当 |
|---|---|---|---|---|
| プロトタイプ | 動くWebアプリ | リポジトリ（`backend/`、`frontend/`、シード） | 区間2〜5 | AIが実装、人間が確認 |
| README | 起動の手順、デモの手順 | `README.md` | 区間2に骨組み、区間5に仕上げ | AIが下書き、人間が確認 |
| `AGENTS.md` | 概要、技術スタック、コマンド | `AGENTS.md` | 区間2 | AIが下書き、人間が確認 |
| 設計資料（提出用・要約版） | MVPスコープと理由、画面構成、データモデル、AI機能の設計、AI活用方法、見送りと次の一手 | `docs/summary.md`（図つき、2〜3ページ） | 区間6 | AIが下書き、人間が確認・修正 |
| AI活用方法の記録 | 指示・分業・レビュー | `docs/ai-dev-log.md`、PRの「AIの関与」欄 | 実装中に随時 | 人間が確認して記録 |

### 3.2 提出用の設計資料（要約版）の構成案

`docs/summary.md` に、2〜3ページ（GitHub上で見る分量）で書く。図はMermaidで描く（GitHubで表示される）。詳細は、既存の `docs/product/` と `docs/adr/` にリンクする。

| 章 | 内容 | 図 |
|---|---|---|
| 1. MVPスコープ | 何を作り、何を見送ったか。最優先にした理由（3〜5行）。中核の流れ | 中核の流れの図、作る／見送るの表 |
| 2. 画面構成・データモデル | 画面の一覧と遷移、主要テーブルの関係、定員を守る仕組み | 画面遷移図、ER図 |
| 3. AI機能の設計 | 役割、実装レベル（モック）とその理由、LLMへの差し替え境界、安全策 | 処理の流れの図 |
| 4. 開発でのAI活用 | どんな指示を出し、何をAIに任せ、どうレビューしたか | 分業の表 |
| 5. 見送りと次の一手 | 見送った機能と理由、本格開発で次にやること | 表 |

### 3.3 AI活用方法の記録の計画
- **指示**: Issue（受け入れ条件つき）と、計画（変更するファイル、方針、テスト方法）をAIに渡し、人間が承認してから実装させる。
- **分業**: 計画・実装・テストの下書きはAI。設計判断、計画の承認、PRのレビュー、最終確認は人間。
- **レビュー**: PRごとに、差分とテスト結果を人間が確認する。手直しが必要だった点は、`docs/ai-dev-log.md` に、原因と対策つきで記録する。繰り返しそうな失敗は、`AGENTS.md` のルールに追加する。
- **指標**: PRごとの所要時間と、AIの出力に手直しした割合を `ai-dev-log.md` の表に記録する。
- 提出の前に、これらを `docs/summary.md` の4章に要約する。

### 3.4 提出の準備（GitHubリポジトリの共有）
- リポジトリは**非公開のまま**、相手をコラボレーター（閲覧）として招待する。招待は、あなた自身が行う。相手のGitHubアカウントが必要になるので、提出先に確認する。
- 提出するブランチは `main` とする。実装のPRをすべてマージしてから共有する。
- 招待の前に、次を確認する。
  - [ ] 履歴にも、実名・マシン名・秘密情報が入っていない（作成者は `isa`、済）
  - [ ] `.env`、鍵、SQLiteのファイルがコミットされていない
  - [ ] 選考の課題文書（PDF）が、コミットされていない（現在は未追跡で、`.gitignore` にも入っていない。どうするかは、実装の開始前に決める）
  - [ ] READMEの手順で、新しい環境から起動できる

## 4. 実装Issueの分け方（1Issue＝1PR）

実際のIssueは、実装の開始時に起票する（GitHubへの操作なので、起票の前に確認を取る）。

| Issue | 内容 | 受け入れ条件の要点 | 区間 | 主なテスト |
|---|---|---|---|---|
| A | 雛形と起動 | バックエンドとフロントエンドが起動し、つながる。`.env.example`。READMEと `AGENTS.md` のコマンド | 2 | 疎通の確認 |
| B | データモデル・シード・暗号化 | テーブルができる。シードで架空の4社などが入る。本番環境ではシードを実行できない。個人情報の列がDBで暗号文 | 3 | #3（DBが暗号文） |
| C | 事業者のログイン・認可 | ログイン、ログアウト、現在の事業者。セッションの失効。他社のデータにアクセスできない仕組み | 3 | #2、#6 |
| D | 体験・便・予約のAPI | 一覧、詳細、予約の作成と確認、承認、却下、連絡先の表示。定員の条件付きUPDATE。マスク。統一したエラー | 3 | #1、#3、#4、#7 |
| E | AIコンシェルジュ（モック） | AIプロバイダーの約束事とモック。`/api/concierge/search` | 3 | #5 |
| F | 旅行者の画面 | トップ、一覧、詳細と予約、完了、予約の確認。スマホ幅で使える | 4 | 型チェック・lint・ビルド、手動 |
| G | 事業者の画面 | ログイン、予約の管理（承認・却下、連絡先の表示） | 4 | 型チェック・lint・ビルド、手動 |
| H | 結合・デモ・設計資料の仕上げ | デモの流れが通る。チェックリストを実施。要約版の設計資料。READMEの仕上げ | 5〜6 | #9 |

- 依存関係: A → B → C、D → E。FはDとEのあと、GはCとDのあと、Hは最後。
- P1の機能（便の中止、集合場所、LLM接続）は、P0が終わって予備枠に入ったときに、別のIssueとして起票する。
- PRを8本に分けると、PR作成にも時間がかかる。PR本文はAIが下書きし、人間が確認する。時間が足りないときは、近いIssue（例: CとD）を、1つのPRにまとめることを検討する（その場合は、理由をPRに書く）。

## 5. 設計フェーズの終わりと、実装の始まり

1. この文書を確定する。
2. 設計フェーズのPR（`docs/1-design-phase`）を作り、Issue #1 を閉じる（`Closes #1`）。レビュー後にマージする。
3. 実装のIssue（A〜H）を起票する。
4. 区間2（環境構築）から、実装を始める。
