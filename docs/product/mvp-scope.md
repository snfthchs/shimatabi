# MVPスコープ

- ステータス: 確定（2026-11-23）
- 関連Issue: #1
- 対象: 目的、利用者の困りごと、中核ユーザーフロー、機能の優先度、MVPで作るもの／見送るもの

時間計画、非機能要件（セキュリティの非機能面を含む）、インフラは設計セッション2で扱う。データモデル、API、画面、AI機能の詳細は設計セッション3で扱う。

## 1. 目的（落とせないところ）

沖縄の小規模な体験事業者と旅行者をつなぐ体験予約プラットフォーム「シマタビ（仮）」のMVPを作る。設計と実装を合わせて4〜6時間で、創業者に早く見せてフィードバックをもらえる状態にする。次の7点は、時間が足りなくなっても外さない。

1. **中核の流れが最後まで動く**: 旅行者が探す、予約リクエストを出す、事業者が確認して承認する、予約が確定する。この一連の流れがデモで通る。
2. **ダブルブッキングを起こさない**: 定員を超える予約は入らない。事業者が最も恐れている点であり、信頼の根幹である。
3. **「作る／見送る」の理由を説明できる**: 機能ごとに、作る理由と見送る理由を文書に残す。
4. **AI機能を1つ入れる**: モック応答でよい。役割と実装レベルの判断理由を残し、LLM APIへ差し替えられる設計にする。
5. **事業者の操作を最小にする**: 現在使っているLINEでのやり取りより面倒にならないことを目指す。
6. **個人情報を守る**: 予約者の個人情報（氏名、電話番号、メール）は暗号化して保存し、画面でも既定で伏せ字にする。管理画面にはログインが必要で、事業者は自分の体験の予約だけを見られる。
7. **公開前提を守る**: 秘密情報や実在の個人情報をリポジトリに入れない。サンプルデータは架空のものにする。

## 2. 前提と制約

- 作業時間は設計と実装を合わせて4〜6時間とする。
- 動かし方は、ローカル実行と画面共有でのデモを必須とする。クラウドは設計のみ行い、時間が余れば対応する。
- AI機能は、まずモック応答で作る。
- 技術スタックの指定は、フロントエンドが TypeScript + React、バックエンドが Python + FastAPI。データベースは任意とする。
- 最初の対象は沖縄本島の事業者10〜20社を想定する。

## 3. 利用者と困りごと

### 3.1 事業者（体験を提供する側）

| 事業者の例 | 困りごと・要望 |
|---|---|
| マリンアクティビティ（1日4便、1便8名） | 空きがあればすぐ確定したい。ダブルブッキングが怖い。天候中止の連絡を人数分電話するのが大変。予約者の連絡先は必ず控えたい。新しいシステムの操作を覚えるのは面倒 |
| 伝統工芸の体験工房（1日2組限定、一人運営） | 勝手に予約が確定すると困るので承認してから確定にしたい。外国人客の問い合わせに英語で返せない。作品の写真をきれいに見せたい |
| 夜の自然ツアー（少人数制） | 集合場所が分かりにくく、毎回説明に苦労している。前日夜の催行判断を、参加者へ一斉に連絡したい。売上に対する手数料は避けたい。リピーターに特別なコースを案内したい |

### 3.2 旅行者（体験を探して予約する側）

- 電話予約はハードルが高い。ネットで完結してほしい。
- 雨で予定が流れたとき、代わりにできる体験をすぐ探したい。
- 子連れで参加できるかを、行く前に確実に知りたい。
- 日本語のサイトしかなく、予約を諦めた（海外からの旅行者）。

### 3.3 創業者の構想

- 大手旅行サイトに載らない小さな事業者を主役にしたい。
- 旅行者がスマホで探して予約できるようにしたい。
- 夢は「AIコンシェルジュ」。「今日の午後、那覇から行ける子連れOKの体験はある？」のような相談に、AIが合う体験を提案する。
- ゆくゆくはオンライン決済、多言語対応、レビュー機能も入れたい。

## 4. 用語（このドキュメントでの意味）

| 用語 | 意味 |
|---|---|
| 体験 | 事業者が提供するアクティビティの内容。名前、説明、料金、集合場所、子連れ可否などを持つ |
| 便（スロット） | ある体験の、ある日・ある時間の1回分。定員は便ごとに持つ。例:「11月30日 9:00の便、定員8名」 |
| 予約 | 旅行者がある便に対して、人数と連絡先を添えて出す申し込み |
| 確定方式 | 予約がどのように確定するか。「即時確定」は空きがあれば予約と同時に確定する。「承認制」は事業者が承認して初めて確定する |
| 催行判断・中止 | 天候などで、その便を実施するか決めること。中止の場合は参加者へ連絡する |

## 5. 今回決めたこと

| # | 決めたこと | 理由 |
|---|---|---|
| 1 | **確定方式は体験ごとに「即時確定／承認制」を切り替えられる**ようにする | 即時確定を望む事業者と承認制を望む事業者の両方がいる。体験に設定項目を1つ持たせて処理を分岐させるだけで済み、実装が軽い |
| 2 | **便の中止と、参加者への一斉連絡はP1**にする | 事業者の共通の困りごとだが、まず中核の流れ（探す→予約→承認）を完成させる。時間が足りないとき最初に縮小する候補にする |
| 3 | **AIコンシェルジュは「探す入口」**にする。自然な文章から条件（日時、場所、子連れなど）を取り出し、体験を絞り込み、提案文を返す | 創業者の構想に直結する。雨天の代替提案や子連れ条件など、旅行者の声を同じ仕組みで扱える。AIは1つに絞り、まずモックで作る |
| 4 | **事業者の体験・便の登録UIは作らず、シードデータで代替**する | 登録UIは開発ボリュームが大きい。予約の流れとAI機能に時間を使う。デモで使う体験と便は事前に登録しておく |
| 5 | **予約者の個人情報（氏名・電話番号・メール）は、保存時に暗号化し、画面でも既定で伏せ字にする** | 事業者は緊急連絡のために連絡先を必ず控えたい。そのため、元に戻せない変換（ハッシュ）は使えず、元に戻せる暗号化を使う。DBが漏れても読めず、画面を覗かれても全体は見えない。AIへの入力（プロンプト）とログには個人情報を入れない |
| 6 | **管理画面はID・パスワードでログインする**。パスワードはハッシュ化して保存し、事業者は自分の体験の予約だけを見られる（認可） | 個人情報を見られる画面なので、最低限の認証と認可が必要。固定トークンより、本格開発への説明がしやすい |
| 7 | **「管理者画面」は事業者の管理画面を指す**。運営（プラットフォーム側）の管理画面はMVPでは作らず、設計のみ行う | 運営の画面は新規に作る画面で重い。MVPの画面は事業者の管理画面に絞る |

## 6. 中核ユーザーフロー

### 6.1 旅行者

1. スマホで体験の一覧を開く。または、AIコンシェルジュに文章で相談する（例:「今日の午後、那覇から行ける子連れOKの体験は？」）。
2. 条件（日付、人数、子連れ可、雨天でも可など）で絞り込んだ結果を見る。
3. 体験の詳細（写真、説明、料金、集合場所、子連れ可否）を見て、空きのある便を選ぶ。
4. 人数と連絡先（氏名、電話番号、メールアドレス）を入力して予約を送る。氏名・電話番号・メールアドレスは、すべて必須とする。
5. 確定方式によって結果が変わる。
   - 即時確定の体験: その場で「確定」と表示される。
   - 承認制の体験: 「承認待ち」と表示され、事業者の承認後に「確定」になる。
6. 予約の状態を、予約番号で確認できる（ログインは不要）。

### 6.2 事業者

1. 事業者の管理画面を開き、ID・パスワードでログインする。ログインした事業者の体験の予約だけが表示される。
2. 自分の体験の予約一覧を、便ごとに確認する。承認待ちの予約が目立つようにする。
3. 承認制の体験の予約を、ワンタップで承認または却下する。
4. 予約者の人数を確認する。連絡先は伏せ字で表示され、「連絡先を表示」を押したときだけ全体を表示する。
5. （P1）天候などで便を中止にし、参加者への連絡文を出す。

### 6.3 予約の状態

| 状態 | 意味 | 次の状態 |
|---|---|---|
| 承認待ち | 承認制の体験で、事業者の確認を待っている | 確定、却下 |
| 確定 | 参加が決まった | キャンセル、（P1）中止 |
| 却下 | 事業者が受けなかった | なし |

- 即時確定の体験は、予約を作ると同時に「確定」になる。
- 承認待ちの予約も、便の定員に数える。却下したときに解放する（[設計の概要](design-overview.md)で決定）。

## 7. 機能別の優先度

- **P0**: 必ず作る。
- **P1**: 中核が動いたあとで、時間があれば作る。
- **P2**: 実装はせず、設計と拡張点だけ考える。
- **見送り**: MVPでは扱わない。理由を残し、議論と次の一手に使う。

インパクトは価値の大きさ（高・中・低）、ボリュームは開発の重さ（S=小、M=中、L=大）を表す。

| 機能 | インパクト | ボリューム | 優先度 | 理由 |
|---|---|---|---|---|
| 体験の一覧・詳細（写真、集合場所、料金、子連れ可否） | 旅行者 高 / 事業者 中 | M | P0 | 探せないと始まらない。写真と子連れ情報は、利用者の声に直接ある |
| 便（日時枠）と定員管理、ダブルブッキング防止 | 事業者 高 | M | P0 | 事業者が最も恐れる点で、信頼の根幹 |
| 予約リクエスト（人数・連絡先） | 旅行者 高 / 事業者 高 | M | P0 | 中核の流れ。連絡先の取得は事業者の必須要望 |
| 事業者の予約管理（一覧・承認・却下） | 事業者 高 | M | P0 | 操作が増えると「LINEのほうが楽」になるため、最小のUIにする |
| 確定方式の切替（即時／承認制） | 事業者 高 | S | P0 | 対立する要望を、小さな実装で同時に満たせる |
| AIコンシェルジュ（探す入口。モック） | 旅行者 高 | M | P0 | 必須要件であり、創業者の構想の中心。まずモックで流れを作る |
| AIコンシェルジュのLLM API接続 | 旅行者 高 | M | P1 | モックで流れが動いたあと、差し替えられる設計にしておき、時間があれば接続する |
| 属性による絞り込み（子連れ可、雨天可） | 旅行者 高 | S | P0 | 体験データの項目として持つだけで、検索とAIの両方に効く |
| 便の中止と、参加者への一斉連絡（通知はモック） | 事業者 高 | M | P1 | 事業者の共通の困りごと。中核の流れの完成が先 |
| 集合場所の案内（説明文＋地図リンク） | 旅行者 中 / 事業者 中 | S | P1 | データ項目の追加だけで効果が出る |
| 予約者の個人情報の保護（保存時の暗号化、画面での既定マスク） | 旅行者 高 / 事業者 高 | M | P0 | 個人情報を扱う以上、外せない。事業者の緊急連絡のため、元に戻せる暗号化を使う |
| 事業者のログイン認証と認可（ID・パスワード、自分の予約だけ閲覧可） | 事業者 高 | M | P0 | 個人情報を見られる画面なので、最低限の認証が必要。旅行者はログイン不要のゲスト予約にする |
| 事業者による体験・便の登録UI | 事業者 高 | L | 見送り（シードで代替） | 重い。デモで使うデータは事前に登録しておく |
| 多言語対応（英語） | 旅行者（海外）高 / 事業者 高 | L | P2 | 価値は高いが重い。データを言語別に持てる設計だけ考えておく |
| 運営の管理画面 | 運営 中 | L | P2 | 新規に作る画面で重い。設計だけ行い、権限の分け方を考えておく |
| 追加のセキュリティ対策（多要素認証、監査ログ、レート制限、データ保持期間） | 中 | M〜L | P2 | 本格開発で必要になる。MVPでは設計のみ |
| 事業者向けのAI問い合わせ自動応答 | 事業者 中 | M | 見送り | AIは1つに絞る。議論用の拡張案とする |
| LINE連携・メールの実送信 | 事業者 高 | L | 見送り | 外部サービスとの連携が重い。通知はモックで流れだけ見せる |
| オンライン決済 | 旅行者 中 | L | 見送り | 構想では「ゆくゆく」の機能。料金モデルの議論が先 |
| レビュー機能 | 低 | M | 見送り | 初期は件数が少なく、価値が出にくい |
| リピーター向けの特別コース | 低 | M | 見送り | 要望が少なく、優先度が低い |

## 8. MVPの定義

### 8.1 作るもの

> 旅行者がスマホで「子連れOKの体験」を探し、予約リクエストを出す。事業者が承認すると予約が確定する。定員を超える予約は入らない。探す入口として、AIコンシェルジュが文章から条件を取り出して体験を提案する。

この一連の流れを、旅行者側と事業者側の両方の画面でデモする。

- 体験の一覧・詳細、属性による絞り込み
- 便と定員の管理、ダブルブッキングの防止
- 予約リクエスト、予約番号による状態確認
- 事業者の予約管理（一覧、承認、却下）
- 確定方式の切替（即時確定／承認制）
- AIコンシェルジュ（モック応答。条件抽出→絞り込み→提案文）
- 予約者の個人情報の保護（保存時の暗号化、画面での既定マスク）
- 事業者のログイン（ID・パスワード）と、事業者ごとの認可
- デモ用のシードデータ（架空の事業者・体験・便）

### 8.2 余裕があれば作るもの（P1）
便の中止と参加者への連絡文、集合場所の案内、LLM APIへの接続。

### 8.3 見送るもの
事業者による登録UI、運営の管理画面（設計のみ）、追加のセキュリティ対策（多要素認証、監査ログなど。設計のみ）、多言語対応（設計のみ）、事業者向けAI自動応答、LINE・メールの実送信、オンライン決済、レビュー、リピーター向けコース。理由は7章の表に記載した。

### 8.4 時間が足りないときに縮小する順番（案）
1. 便の中止と一斉連絡（P1）をやめる
2. LLM APIへの接続（P1）をやめる（モックのまま）
3. 集合場所の案内（P1）を、説明文だけにする

P0の機能は縮小しない。個人情報の保護と認証・認可もP0なので、縮小の対象にしない。この順番は、設計セッション2で時間計画と合わせて確定する。

## 9. 未決事項・確認したいこと

| # | 内容 | 案 | 決める場所 |
|---|---|---|---|
| 1 | 承認待ちの予約は、定員を押さえるか | 押さえる（承認待ちも定員に数える）。却下したときに解放する | [設計の概要](design-overview.md)で決定 |
| 2 | 旅行者が予約を確認する方法 | 予約番号と連絡先（電話番号またはメール）の組み合わせ。ログインは不要。連絡先は暗号化されているので、予約番号で予約を取得したあとに復号して比較する | [設計の概要](design-overview.md)で決定 |
| 3 | AIコンシェルジュのモック応答の仕組み | キーワード（地域、子連れ、雨、時間帯）から条件を取り出す規則ベース。LLM接続時に同じ入出力で差し替える | [設計の概要](design-overview.md)で決定 |
| 4 | 創業者への確認: 承認制を望む事業者はどのくらいの割合か | 確認する。確定方式の切替が必要な根拠になる | デモ・ディスカッション |
| 5 | 創業者への確認: 連絡手段としてLINEをどこまで想定するか | 確認する。通知の実送信を後回しにした判断の確認になる | デモ・ディスカッション |
| 6 | 創業者への確認: 事業者の料金モデル（手数料か月額固定か） | 確認する。決済を見送った判断に関わる | デモ・ディスカッション |
| 7 | 暗号化の方式と鍵の管理 | MVPは環境変数（`.env`）に鍵を置き、コミットしない。本格開発ではマネージドの鍵管理サービスを使う | [ADR 0004](../adr/0004-pii-encryption-and-masking.md)で決定 |
| 8 | 暗号化した項目の検索 | 暗号化した項目では、検索や並べ替えができない。事業者の画面は、便・状態・予約番号で探せる設計にする | 設計セッション3（データモデル） |
| 9 | ログイン状態の持ち方と、パスワードのハッシュ方式 | サーバー側セッション＋HttpOnly Cookie、パスワードはargon2id | [ADR 0003](../adr/0003-authentication-session.md)で決定 |
