# 0008. クラウド版プロトタイプは、AWSの非公開構成とキーを使わない認証で作る

- ステータス: 承認
- 日付: 2026-11-28

## 背景
プロトタイプは、開発PC上で動かし、画面共有でデモする作りである。開発PCを持ち運ばずにデモできるように、クラウドに置きたい。

前提は次のとおりである。

- 利用者は限られた人にする。利用は、1日3時間程度を1週間程度である。
- 扱うのは架空のデータだけである。
- 費用は、できるだけかけない（LLMの利用料は別とする）。
- インフラはコードで用意し、画面での操作は、初回の準備に限る。
- クラウドは1つにする。人間が慣れているAWSかAzureから選ぶ。
- データベースはアプリと分ける。
- デモであっても、基本の構成は本番に近づける。可用性と負荷分散は考慮しない。
- できるだけ、長期のキーを使わずに認証する。

## 選択肢

### クラウド
| 案 | 良い点 | 悪い点 |
|---|---|---|
| AWS | 非公開のネットワークで、王道の構成を組める。新規利用者向けのクレジットがある | 部品が多く、構築の手間がかかる |
| Azure | App Serviceを使えば、少ない部品で、HTTPSとIPの制限まで用意できる | クレジットの期間が30日と短い。今回は、構成の練習も兼ねてAWSを選んだ |

### APIの実行
| 案 | 良い点 | 悪い点 |
|---|---|---|
| ECS Fargate | コンテナをそのまま動かせる。常時起動で、DBの接続を使い回しやすい。本番の想定（コンテナ）に近い | ALBなどが必要で、常時料金がかかる |
| Lambda | 料金が安く、部品が少ない | FastAPIを動かすための部品が要る。実行数が増えると、DBの接続も増える。起動の待ち時間がある |

### データベース
| 案 | 良い点 | 悪い点 |
|---|---|---|
| RDS for PostgreSQL | 一般的なPostgreSQLで、予約の定員の処理の考え方を活かせる | 常時料金がかかる |
| Aurora DSQL | 毎月の無料の範囲がある | PostgreSQLと違いがあり、同時更新の扱いを見直す必要がある |
| サーバー内のSQLite | コードの変更が少ない | タスクの入れ替えで、データが消える。データベースを分ける前提に合わない |

### 外向きの通信
| 案 | 良い点 | 悪い点 |
|---|---|---|
| NAT Gatewayを使う | アプリを非公開サブネットに置ける。設定を誤っても、外から直接は届かない | 常時料金がかかり、構成の中で占める割合が大きい |
| タスクに公開IPを持たせる | 安い | 受信の制限がセキュリティグループだけになり、設定を誤ると直接届く |

### 認証
| 案 | 良い点 | 悪い点 |
|---|---|---|
| IAMロールと短命のトークン | 長期のキーを配らず、漏えいしたときの影響が小さい | 設定とコードの変更が要る |
| APIキーとパスワードを保存する | 今のコードのまま使える | キーの管理と入れ替えが要る |

### 構成の管理
| 案 | 良い点 | 悪い点 |
|---|---|---|
| Terraform | 作成と削除を、コードで再現できる。ほかのクラウドでも使える | 状態ファイルの管理が必要になる |
| AWS CDK | 一般のプログラミング言語で書ける | AWSに限られる |
| 画面で作る | 準備が少ない | 再現できず、削除の漏れが起きやすい |

### インフラのコードと文書の置き場所
| 案 | 良い点 | 悪い点 |
|---|---|---|
| このリポジトリにまとめる | 1か所で読める | 公開リポジトリに、権限や残るリスクの詳細が載る |
| 非公開の別リポジトリに分ける | 詳細を公開せずに済み、コードと文書を一緒に直せる | リンク先を、ほかの人は開けない |
| 両方に同じ内容を置く | どちらからも読める | 片方だけが直され、食い違う |

## 決定
**AWSで、次の構成にする。** 概要は、[クラウド版プロトタイプの構成（概要）](../product/cloud-prototype-infra.md)に書く。

| 項目 | 決めたこと | 理由 |
|---|---|---|
| 入り口 | CloudFrontとWAF。許可したIPだけを通す | 入り口を1つにして、画面とAPIを同じオリジンにする |
| 画面 | S3から配信する | 本番に近い構成にする |
| API | 内部ALBと、ECS Fargate（タスク1つ） | コンテナで本番に近づける。ALBは、固定の接続先、死活確認、デプロイ時の入れ替えに必要で、内部にすることでWAFの回り込みを防ぐ |
| データベース | RDS for PostgreSQL（シングルAZ） | 一般的なPostgreSQLを使う |
| 外向きの通信 | NAT Gatewayを使う | 本番に近く、設定の誤りに強い。短い期間の利用なら、クレジットの範囲に収まる見込みである |
| 認証 | IAMロール、IAMデータベース認証、GitHub ActionsのOIDC、LLMはWorkload Identity Federation | 長期のキーを使わない |
| 冗長化 | しない | デモの前提で、可用性と負荷分散は考慮しない |
| 構成の管理 | Terraform。画面の操作は、初回の準備に限る | 作成と削除を再現できる |
| アプリのデプロイ | 非公開の別リポジトリのワークフローが、このリポジトリのコードを取得して反映する | このリポジトリに、AWSの権限を持たせない |
| 置き場所 | インフラのコードと詳細な設計は、非公開の別リポジトリ。このリポジトリには、概要と理由を置き、同じ内容を両方には書かない | 権限やリスクの詳細を公開しない。コードと文書を一緒に直せる |

この構成は、ADR 0007の「キーの有無でLLMとモックを切り替える」という作りに、キーを使わない接続を追加することになる。実装のときに、切り替えの条件を見直す。

## 結果
- 利用者の入り口がCloudFrontだけになり、アプリとデータベースは非公開になる。
- 長期のAPIキーを、クラウドに置かずに済む。残る秘密情報は、個人情報の暗号化の鍵、データベースの管理者パスワード、デモ用のパスワードである。
- 常時料金がかかる部品が多く、利用が短くても料金が下がりにくい。使い終わったら削除する必要がある。
- PostgreSQLへの切り替え、Cookieの設定、シード、LLMの認証などの、コードの変更が必要になる。
- インフラの詳細は、このリポジトリを読むだけでは分からなくなる。
- 利用するAWSのプランで、選んだサービスが使えるかは、確認できていない。アカウントを作るときに確認し、使えない場合は、プランか構成を見直す。
- 本番の構成（冗長化、監視、独自ドメインなど）は、別に検討する。
