# 0002. 技術スタックとデータベース

- ステータス: 承認
- 日付: 2026-11-23

## 背景
- 技術スタックの指定は、フロントエンドが TypeScript + React、バックエンドが Python + FastAPI。データベースは任意。
- 作業時間は設計と実装を合わせて4〜6時間で、ローカル実行と画面共有でデモする。
- 予約の定員を守る（ダブルブッキングを起こさない）ことが、最も重要な要件の1つである。
- 本格開発ではクラウド（コンテナ実行）に移すため、ファイルのDBは使えず、PostgreSQLなどに切り替える前提になる。

## 選択肢

### データベース
| 案 | 良い点 | 悪い点 |
|---|---|---|
| A. SQLite＋ORM | ファイル1つで動き、準備が軽い。ORMを通せば後から差し替えやすい | 行ロック（`SELECT ... FOR UPDATE`）が効かず、型や日時の扱いがPostgreSQLと違う。クラウドではそのまま使えない |
| B. PostgreSQL（Docker Compose） | 本番と同じ種類で、切り替えが不要 | Dockerの準備と起動の手間が増える（目安で15〜30分）。5時間の中では重い |
| C. DBなし（メモリ上やJSONファイル） | 最も軽い | 整合性（定員）を見せられず、設計力の評価に結びつきにくい |

### フロントエンドの見た目
| 案 | 良い点 | 悪い点 |
|---|---|---|
| Tailwind CSS | スマホ向けの画面を素早く作れ、見た目の自由度が高い。依存が少ない | 部品は自分で組む |
| MUIなどのUIライブラリ | 部品がそろっている | 見た目の癖が強く、調整に時間がかかることがある |

## 決定

### 採用する構成
- フロントエンド: React、TypeScript、Vite、React Router、TanStack Query、Tailwind CSS
- バックエンド: FastAPI、Pydantic、SQLAlchemy 2.x
- データベース: **SQLite（案A）**。DBへのアクセスはORMのみとする
- 型の共有: FastAPIのOpenAPIから、TypeScriptの型を生成する。遅れたら手書きの型で代替する
- リポジトリの構成: `backend/`、`frontend/`、`docs/`

### PostgreSQLに切り替えやすくするためのルール
1. SQLは書かず、ORMを通す（生SQLを使わない）。
2. **定員の更新は条件付きUPDATEで行う。** 「`booked + 人数 <= capacity` のときだけ加算し、更新された行数を確認する」という1回の命令で、判定と更新を終える。行ロックに頼らない。
3. 日時は、UTCでタイムゾーン付きとして保存・処理する。表示するときに日本時間へ変換する。
4. 列の型は、ORMのモデルで明示する。
5. 時間が余れば、テストをPostgreSQLでも一度流す。

### 保留にするもの
Pythonのパッケージ管理、テスト・lint・型チェックのツールは、実装の開始時、またはテスト計画の相談で決める。

## 結果
- 準備が軽く、5時間の中で予約の流れとAI機能に時間を回せる。
- 上のルールを守れば、PostgreSQLへの切り替えは、接続先の変更と、型・日時まわりの確認が中心になる。このMVPは実データを持たず、データはシードで作り直せるので、データの移行は不要である。
- SQLiteでは、並行アクセスのときの行ロックの動きをデモできない。ただ、条件付きUPDATEは1回の命令で判定と更新が終わるので、定員を守る仕組みの見せ方は変わらない。
- ルールを破った書き方が入ると、PostgreSQLへの切り替え時に定員の整合性が崩れる。レビューで確認する。
