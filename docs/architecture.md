## 1. セットアップの補足
- 予約者の個人情報（氏名・電話・メール）を暗号化する鍵（`PII_ENCRYPTION_KEY`）がないと、バックエンドは起動しない。起動のときに、原因が分かるエラーになる。
- 鍵は、コミットしない。鍵をなくすと、暗号化した個人情報は読めなくなる（デモ用のDBは、シードで作り直せる）。
- 鍵は、カンマ区切りで複数書ける。先頭の鍵で暗号化し、すべての鍵で復号を試す（鍵を入れ替えるときに使う）。
- シードの `--reset` は、すべてのテーブルを消して作り直してから投入する。`--reset` なしは、空のDBにだけ投入する。
- シードで作る今日の便は、実行した時刻より後のものだけである。夕方以降に入れると、「今日の午後」の便がない。
- `.env` の `APP_ENV=production` のときは、シードを実行できない。
- DBのファイルは `backend/data/shimatabi.db` にできる（コミットされない）。

## 2. 画面の補足
フロントエンドの開発サーバーが、`/api` をバックエンドへ転送する。画面とAPIは、同じオリジンで動く。APIの文書は、http://localhost:5173/api/docs で見られる。

### 2.1 旅行者の画面
- 一覧の絞り込み（日にち・人数・エリア・種類・子連れOK・雨でもOK）の条件は、URLに入る。
- 詳細は、`?slot=ID` で、便を選んだ状態で開ける（AIの提案のカードから来るとき）。
- 予約の完了（`/bookings/complete`）は、予約の直後だけ表示される。再読み込みすると、予約の確認へ誘導する。
- 氏名・電話・メールは、予約の送信と状態の確認のときだけ送る。URL・`localStorage`・`sessionStorage` には残さない。完了の画面へは、ルーターの `state` だけで渡す。
- 日時は、UTCで受け取り、画面で日本時間に直す。
- 体験の写真は、仮の画像（`frontend/public/photos/`、自作のイラスト）である。実際の写真は、事業者から提供を受けたものに差し替える想定。
- 画面は、スマホ幅を基本にして、PC幅（1024px以上）にも対応している（[ADR 0005](adr/0005-responsive-layout.md)）。

### 2.2 事業者の画面
- 未ログインで `/admin/bookings` を開くと、`/admin/login` へ戻る。ログアウトすると、サーバー側のセッションを消し、画面に残ったデータも捨てる（`['admin']` のキャッシュを消す）。
- 氏名・電話・メールは、伏せ字で表示する。「連絡先を表示」を押したときだけ、その1件の平文を取得し、その行の部品の状態にだけ持つ。URL・ブラウザの保存領域・TanStack Queryのキャッシュには残さない。「連絡先を隠す」で、伏せ字に戻る。
- 却下は、確認の操作（2段階）を挟む。
- すでに処理された予約を、承認・却下しようとしたときは、「すでに処理されています」と表示して、一覧を更新する（APIは、409 `INVALID_STATE`）。
- 電話番号は、ハイフンなしで保存される。そのため、伏せ字は `090****5678` の形になる。

### 2.3 APIの型
APIの型は、バックエンドのOpenAPIから生成して、`frontend/src/api/schema.d.ts` に置いている（手で編集しない）。APIの入出力を変えたら、バックエンドの仮想環境を作ったあとで、次を実行して、生成し直す。

```bash
npm --prefix frontend run gen:api
```

## 3. API
エラーは、すべて `{"error": {"code": "...", "message": "..."}}` の形で返る。日時のレスポンスは、UTC（`Z` つき）。

### 3.1 旅行者向け（ログイン不要）
| メソッド | パス | 内容 |
|---|---|---|
| GET | `/api/experiences` | 体験の一覧。クエリ: `date`（日本時間の日付）、`party_size`、`kids_ok`、`rain_ok`、`area`、`category`、`max_minutes_from_naha`。条件に合う受付中の便を持つ体験だけを返す |
| GET | `/api/experiences/{id}` | 体験の詳細と、これから始まる受付中の便（満席は残席0で含む） |
| POST | `/api/bookings` | 予約を作る（201）。氏名・電話・メールは、すべて必須。即時確定の体験は確定、承認制の体験は承認待ちになる |
| POST | `/api/bookings/lookup` | 予約番号と連絡先（電話またはメール）で、予約の状態を確認する。連絡先は個人情報なので、URLではなくPOSTの本文で送る |
| POST | `/api/concierge/search` | AIコンシェルジュ。本文は `{"message": "…"}`（1〜500文字）。文章から検索条件を取り出し、条件に合う体験を、理由つきで提案する。予約は実行しない |

### 3.2 事業者向け（要ログイン）
自社のデータだけを対象にする。他社のデータは、存在しないもの（404）として扱う。

| メソッド | パス | 内容 |
|---|---|---|
| POST | `/api/admin/login` | ログインIDとパスワードでログインする。セッションのCookieが設定される |
| POST | `/api/admin/logout` | ログアウトする（サーバー側のセッションを削除し、Cookieを消す） |
| GET | `/api/admin/me` | ログイン中の事業者の情報を返す |
| GET | `/api/admin/slots` | 自社の便と、便ごとの予約の状況（承認待ち・確定の人数） |
| GET | `/api/admin/bookings` | 自社の予約の一覧。氏名・電話・メールは、サーバー側でマスクして返す |
| POST | `/api/admin/bookings/{id}/approve` | 承認待ちの予約を承認する |
| POST | `/api/admin/bookings/{id}/reject` | 承認待ちの予約を却下し、押さえていた定員を解放する |
| GET | `/api/admin/bookings/{id}/contact` | 1件の予約の連絡先を、平文で返す（「連絡先を表示」） |

- セッションの有効期限は8時間（固定）。Cookieは `HttpOnly`、`SameSite=Lax`（HTTPSのときは `Secure`）。
- ログインの失敗は、IDとパスワードのどちらが違うかを、伝えない。

## 4. 守っている決まり
- **定員は、条件付きUPDATEで守る。** 便の `booked_count` は、`backend/app/services/bookings.py` の条件付きUPDATEだけで書き換える。承認待ちの予約も、定員に数える。満席・開始後・中止の便への予約は、409（`SLOT_UNAVAILABLE`）。
- **個人情報は、暗号化して保存する。** マスクは、サーバー側で行う。ログ・URL・AIへの入力には、出さない（[ADR 0004](adr/0004-pii-encryption-and-masking.md)）。
- **事業者向けのAPIは、ログイン中の事業者のデータだけを対象にする**（[ADR 0003](adr/0003-authentication-session.md)）。
- **DBは、ORMだけで扱い、生SQLを書かない**（[ADR 0002](adr/0002-tech-stack-and-database.md)）。

## 5. AIコンシェルジュの仕組み
例: 「明日の午後、那覇から行ける子連れOKの体験ある？」と送ると、`conditions`（読み取れた条件）、`suggestions`（提案。体験・便・理由）、`reply`（返答の文章）が返る。

- 流れは、①文章から条件を取り出す（AIプロバイダー）→ ②**アプリがDBを検索する** → ③返答文を作る（AIプロバイダー）。**検索と予約は、AIに任せない**ので、提案は、必ずDBにある体験と受付中の便だけになる。理由（子連れ可、那覇からの時間、残席など）は、DBの事実からアプリが作る。
- 条件に合う便がないときは、条件を1つずつ外して再検索し、件数のある緩め方（「雨の条件を外すと1件あります」）を返す。条件が読み取れないときは、一覧へ誘導する文を返す。
- 現在のAIプロバイダーは、**ルールベースのモック**（LLMを使わない）。環境変数 `AI_PROVIDER` は、`mock`（既定）。`llm` は、まだ実装されておらず、指定すると、起動のときにエラーになる。読み取れる言葉は、`backend/app/ai/mock_provider.py` の冒頭にある。
- 旅行者の文章は、**ログに残さず**、応答にも含めない。AIには、文章と現在時刻だけを渡す（予約者の個人情報は渡さない）。
- 設計は、[設計の概要](product/design-overview.md)の6章にある。
